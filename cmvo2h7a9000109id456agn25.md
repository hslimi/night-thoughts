Most fine-tuning tutorials end when training loss decreases.

I wanted to answer a more interesting question: given a synthetic patient’s symptoms, can a small local model learn not only what is most likely—but what else it could be?

I fine-tuned **Qwen2.5-1.5B-Instruct** on **English DDXPlus** using native **MLX LM** and **QLoRA-style adaptation**. Then I compared the base and fine-tuned models on identical held-out cases, removed a finding to test the adapter’s sensitivity, fused the adapter, and deployed the result through **oMLX** and **QwenPaw**.

This is an educational machine-learning experiment on synthetic cases—not a clinical tool and not medical advice.

## Foundation: the local serving stack

This experiment builds on the always-on local serving foundation described in my [Complete Guide to an Always-On Mac Server with MLX, oMLX, and QwenPaw](https://nightthoughts.me/complete-guide-always-on-mac-server-with-mlx-omlx-qwenpaw). If you still need to install or configure that stack and its background services, start there. This article assumes that foundation for the deployment stage and focuses on the DDXPlus data, QLoRA-style training, held-out evaluation, and reversible integration.

## The mental model before we start

I did not train a language model from scratch. I started with a pretrained general-purpose instruct model: earlier training had already given it language and instruction-following capabilities. I then specialized its behavior using synthetic DDXPlus examples and kept the original base model unchanged for comparison.

The experiment covers four different questions:

- **Data preparation:** can I turn coded synthetic cases into faithful training examples without mixing the official splits?
- **Adaptation:** can a small adapter learn the constrained response behavior while the base weights remain frozen?
- **Behavioral evaluation:** do label agreement and response structure improve on withheld cases, rather than only improving the loss curve?
- **Deployment:** can I serve and use a standalone artifact, then restore the previous application configuration?

```text
Pretrained instruct model + decoded DDXPlus examples
                         ↓
               Train a small adapter
                         ↓
Base vs base + adapter on identical held-out cases
                         ↓
      Verified fused model → oMLX → QwenPaw
```

“Teaching the model to think in differentials” is an experimental metaphor. The model is trained to produce a most-likely dataset label and ranked alternatives, not a clinician-style reasoning trace.

### What is in a DDXPlus row?

Each row represents a synthetic patient case, not a real person’s record. The important fields are:

| Field | What it means in this experiment |
| --- | --- |
| `PATHOLOGY` | The dataset’s reference label for the case. |
| `DIFFERENTIAL_DIAGNOSIS` | Source-derived alternative labels used for the reference differential and ranked targets. |
| `EVIDENCES` and `INITIAL_EVIDENCE` | Coded findings supplied with the synthetic case. |
| `release_evidences.json` | The dictionary that translates those codes and their values into readable English questions or findings. |

When I use “ground truth” below, I mean the dataset’s `PATHOLOGY` reference label—not absolute medical truth or an independently verified diagnosis.

Symptoms describe the case’s current reported findings. Antecedents describe relevant history or background, such as earlier conditions or exposures. Both are supplied as evidence to the model; neither independently proves the reference label.

## Part 2: Prepare the datasets

### From a raw row to a training example

The transformation looks like this:

```text
Raw dataset row → decoded evidence → user prompt → target response
```

A system message defines the closed label set and required response sections. The user prompt describes the decoded synthetic case: age, sex, symptoms, and antecedents. The target response is the assistant example used during training. For training examples, it places `PATHOLOGY` in the most-likely section, builds three ranked differential entries from the supplied labels, and ends with the fixed uncertainty statement. I am formatting source-derived labels, not writing a clinician-style rationale.

During training, these prompt-and-target pairs teach the desired behavior. During evaluation, the model receives the system and user messages without the target response; its generated answer is what I score.

I did not train on the full training release. The experiment uses deterministic, stratified subsets sampled inside each official split:

| Split | Cases per pathology | Total |
| --- | --: | --: |
| Train | 40 | 1,960 |
| Validation | 10 | 490 |
| Test | 10 | 490 |

### Why the splits stay separate

Think of training as practice, validation as progress checks, and testing as a final problem set that must stay out of the practice material. In this experiment:

- **Train** examples update the adapter.
- **Validation** examples monitor training through validation loss; they do not update the adapter.
- **Test** cases are withheld for the final behavioral comparison.

Identical prompts across splits would be data leakage. A test prompt that had already appeared in training could reward memorization and inflate the results instead of measuring behavior on unseen cases.

Stratified sampling means sampling per pathology within each official split. Every one of the 49 labels is represented, rather than relying on an uncontrolled random subset that might miss or underrepresent labels. Equal per-label counts are an experimental design choice, not a claim about real-world prevalence.

The seed is 42. Official test patients are never moved into training. The final preprocessing also replaces duplicate decoded prompts with other eligible rows from the same official split and class, so all three prompt sets are unique and disjoint.

`prepare_ddxplus.py` uses `ast.literal_eval` for CSV list fields, never `eval`. Numeric evidence values retain their decoded values, while categorical `N` becomes `No`. Symptoms and antecedents stay separate.

One data edge case matters: the dataset spelling `Larygospasm` has only two usable reference differential labels in the selected validation and test cases. The preprocessing permits a two-item target there rather than inventing a third label. Training targets still contain exactly three source-derived labels. The evaluator still requires exactly three ranked predicted labels for a structured response, so a two-label prediction fails that strict format metric even in these cases.

The preprocessing command verifies and reuses a complete set of valid generated files. It stops if files are incomplete or their metadata, structure, split isolation, or pinned test hash differs. Replacing generated files requires inspecting them and explicitly running `python prepare_ddxplus.py --overwrite-generated`; that flag was not used for this run.

## Part 3: Smoke-test generation and evaluate the base model

### Why measure the base first?

The base model already has general language and instruction-following capabilities from its earlier training. That does not tell us whether it can follow this particular closed-set differential format or agree with DDXPlus labels. I need to measure that starting point before adding the adapter. Without a baseline, I could not attribute a later improvement to the adapter rather than to the prompt or task setup alone.

The evaluator uses the pinned MLX conversion at revision `8b403126fc14f14cfc99bb4cfa72ecbc129ea677`. It applies the same chat template, system prompt, greedy generation, and 220-token limit in every mode.

### What the metrics mean

- **Top-1 accuracy:** was the first predicted label the dataset label?
- **Top-3 accuracy:** did the dataset label appear among the three ranked alternatives?
- **Structured-response rate:** did the model follow the requested sections and three-item ranked output contract?
- **Reference overlap@3:** how many of the predicted alternatives also appear in the source reference differential? The summary reports the mean across cases.

Formatting accuracy and label agreement are different. A perfectly formatted answer can still have the wrong top-1 label; a correct label can also appear in a response that fails the format check. I report those behaviors separately.

The first command is only a three-case generation smoke test. Its output is kept under a separate prefix and is not a benchmark result.

## Part 4: Smoke-test training and train the full adapter

### LoRA and QLoRA in this experiment

A model’s weights are the numerical parameters it uses to generate responses. Full fine-tuning would update the base model’s weights directly. LoRA instead leaves those weights fixed and trains a much smaller set of additional parameters: the adapter. The adapter is not a standalone model; adapter evaluation loads the base model and adapter together.

Quantization reduces the numerical precision used to store the base weights. In this experiment, “QLoRA-style” means training a LoRA adapter on top of that quantized base. The original base remains available for comparison, while the learned adjustment lives in the separate adapter.

The training smoke test uses a separate adapter directory and only two iterations. It verifies that training and adapter saving work; its losses are not final training results. The full adapter and full training log are guarded against accidental replacement. For fresh reproduction, `pinned_base_path()` resolves the same pinned model revision to its local snapshot for training and fusion. The saved original training configuration names the upstream hub ID; I did not rerun training to change that record.


The full run used a quantized base with LoRA adapters on eight layers, rank 8, scale 20.0, dropout 0.0, the Adam optimizer, batch size 2, gradient accumulation 4, learning rate `1e-5`, and maximum sequence length 2048. Prompt masking and gradient checkpointing were enabled. The batch-size-one fallback was not used.

### Reading the training settings

- **Rank 8** controls the adapter’s capacity: how much trainable flexibility is available for the adaptation.
- **Eight adapted layers** limit which parts of the network receive adapter components. The base weights remain frozen throughout.
- **Prompt masking** leaves the patient prompt out of the training loss, so optimization focuses on producing the desired response rather than reproducing the input.
- **Gradient accumulation** combines gradients from several small batches before an update, simulating a larger effective batch without processing all of those examples simultaneously.
- **Gradient checkpointing** recomputes some intermediate values instead of retaining them all, trading additional computation for lower training-memory pressure.

The first reported training loss was **2.056 at iteration 10**, and the final training loss was **0.057 at iteration 1,200**. Validation loss was **2.257 at iteration 1** and **0.064 at iteration 1,200**. Iteration 1 is a validation measurement, not an initial training-loss report.

### Why we did not stop at the loss curve

Loss measures token-prediction error under the training objective: how closely the model’s predicted tokens match the target responses. A falling loss says that optimization is fitting that objective better.

It does not directly tell us whether the first predicted pathology is correct, prove that the requested response format is followed, or establish behavior on unseen cases. That is why the held-out evaluation is the more meaningful behavioral result: it checks labels and structure on cases that did not update the adapter.

## Part 5: Inspect disagreements and run an evidence-ablation probe

A better aggregate score does not explain every changed prediction. The comparison found **440 top-1 disagreements**, **404 cases improved from incorrect to correct**, and **one regression from correct to incorrect**. Fifty cases retained the same top-1 label.

### What does evidence ablation test?

The question is simple: **if we remove one relevant finding, does the prediction change?** I compare the original prompt with the same prompt after one controlled edit, keeping the model and generation settings fixed.

This tests sensitivity to that prompt change. An unchanged response is a useful behavioral observation for this case. It does not create a new medical ground truth for the edited case, prove causality, or explain the model’s internal reasoning. It is not a second accuracy benchmark: there is no newly validated label against which to score the edited response.

## Part 6: Fuse and independently verify the standalone model

### Why fuse, and why verify?

An adapter normally has to accompany its original base model: inference loads the base weights and applies the learned adapter adjustment. Fusion combines that adjustment into a standalone model artifact, which is simpler to copy and deploy because the serving layer no longer needs a separate adapter path.

That packaging change should not be trusted blindly. Numerical conversion can change generated responses, so the standalone artifact needs the same behavioral evaluation as the adapter. The first quantized fused artifact was rejected because its independent results diverged sharply from the adapter’s. I therefore evaluated a separate dequantized artifact instead of assuming that fusion had preserved behavior. Even after that correction, `reviewed_with_differences` means that known differences passed an explicit review—not that the two models are exactly equivalent.

The original `mlx_lm.fuse` command produced a quantized fused artifact that behaved very differently from the adapter. I rejected it rather than deploying it. Its full 490-case results were:

| Metric | Rejected quantized fused |
| --- | --: |
| Top-1 accuracy | 16.94% |
| Top-3 accuracy | 23.88% |
| Structured-response rate | 0.00% |
| Mean reference overlap@3 | 0.335 / 3 |

The correction was to create a **separate dequantized artifact** with `--dequantize`; I did not retrain or overwrite the full adapter. The following block creates and independently evaluates that artifact, then applies the strict response-identity check. A strict mismatch stops deployment.

```bash
bash &lt;&lt;'BASH'
```

## Part 7: Deploy through oMLX and connect QwenPaw

### Which component does what?

| Component | Role in this experiment |
| --- | --- |
| MLX LM | Training and direct local evaluation |
| LoRA adapter | Learned task-specific adjustment |
| Fused model | Standalone deployable model artifact |
| oMLX | Local inference server and OpenAI-compatible API |
| QwenPaw | Agent/application layer that calls the configured model |

In short, the adapter contains the learned adjustment, the fused model packages it for deployment, oMLX serves generation requests, and QwenPaw is the application using that service.

The deployment helper verifies the reviewed fused artifact and its file hashes, installs only the experiment model, and restarts the existing **system LaunchDaemon** directly. It does not use Homebrew services or modify unrelated model registrations. The forced restart briefly interrupts oMLX-served models and active requests. The helper discovers the exact model ID through `/v1/models` and uses that returned ID in the generation request.

The restart inside the helper is `sudo launchctl kickstart -k system/com.omlx.server`. If you have just performed that restart yourself, use `python deploy_omlx.py --case-id test-0001 --skip-restart` instead of restarting it again in the block below.

## Part 8: Test rollback

Reversibility is part of reproducible engineering. An experiment should not require permanently sacrificing the previous working configuration just to test a new model. A tested rollback gives me a way back to that known state and makes the final system state explicit.

Before changing QwenPaw, the helper saved both the global configuration and the selected agent’s configuration, plus the original provider model registrations and removal list. Rollback restores those saved states, preserves unrelated settings, and removes the experiment’s QwenPaw model registration. It retains the trained adapter and fused model.

The following form uses the same real system daemon restart that I verified. The forced QwenPaw restart briefly interrupts sessions and active requests; the rollback verifier checks that the restarted process began after preparation:

```bash
bash &lt;&lt;'BASH'
set -euo pipefail
cd "$HOME/night-thoughts/experiments/ddxplus-mlx-lora"
source .venv/bin/activate
mkdir -p results/logs
exec &gt; &gt;(tee -a results/logs/part8.log) 2&gt;&1

python qwenpaw_model.py --prepare-rollback
sudo launchctl kickstart -k system/com.qwenpaw.app
python qwenpaw_model.py --verify-rollback
BASH
```

I also used **Restore default model** in the experiment chat to clear its per-chat override and confirmed that the original response remained visible. No new response was generated. QwenPaw’s original global and per-agent selections were restored, and the configuration files matched their backups exactly.

QwenPaw may refresh only `capability_provenance`, `discovered_at`, and `released_at` during model discovery. Durable model settings and selections must still match. The explicitly requested permanent oMLX credential repair remains synchronized; rollback does not bring back the stale key. The deployed oMLX model was retained, and the optional model-removal block was not run.

&gt; **What just happened?** oMLX served the fused model, and QwenPaw completed a real chat through the configured backend. Rollback then restored the previous model selections while retaining the trained artifacts and the intentional credential repair.

## Limitations

This experiment cannot establish clinical usefulness.

- DDXPlus patients are synthetic.
- The task is limited to the 49 dataset pathology labels.
- Real patients may have multiple conditions or incomplete histories.
- The stratified subset does not preserve the dataset’s original prevalence.
- Agreement with a reference differential is not clinical validation.
- Ten held-out `Larygospasm` cases have two reference labels; no third label was invented.
- Edited ablation cases do not automatically have valid labels.
- A confident and well-formatted answer can still be wrong.
- A successful oMLX or QwenPaw round trip is not a clinical evaluation.

The resulting model must not be used to diagnose, triage, or recommend care for a real person.

## Final thoughts

The goal was not “a doctor on my Mac.” It was a complete local workflow with evidence at every stage, from authentic source data and split isolation through deployment and rollback. That is a much stronger result than an attractive training-loss curve—and a much more honest starting point for experimenting with diagnostic language models locally.

### What this experiment demonstrated

- A compact local model can be adapted to a constrained synthetic differential-response task.
- Evaluation must measure behavior on held-out cases, not only loss.
- Deployment artifacts need independent verification; the rejected fusion shows why.
- Local deployment, application integration, and rollback can be tested end to end.

### What it did not demonstrate

- Clinical validity.
- Real-patient performance.
- Clinician-style reasoning.
- Generalization beyond this selected DDXPlus setup.
- Equivalence between QwenPaw and direct oMLX responses.

## Compact glossary

- **Base model:** the pretrained general-purpose instruct model that provides language and instruction-following capabilities before this experiment. It remains the comparison point.
- **Quantization:** representing model weights with lower numerical precision. This run used a 4-bit MLX conversion of the base model.
- **LoRA:** Low-Rank Adaptation, a method that trains a relatively small set of additional parameters while leaving the base weights frozen.
- **QLoRA:** in this experiment, QLoRA-style training means training a LoRA adapter on top of the quantized base.
- **Adapter:** the learned task-specific adjustment that must normally be loaded together with its base model. It is not a standalone model.
- **Evidence:** a supplied finding from a synthetic case, such as a symptom or antecedent, decoded from the dataset’s coded fields.
- **Ground truth:** the dataset’s reference `PATHOLOGY` label, not absolute medical truth.
- **Held-out case:** a case withheld from adapter training and used for behavioral evaluation; here, one of the selected 490 test cases.
- **Fusion:** merging the learned adapter adjustment into a standalone model artifact. The fused artifact still needs independent behavioral verification.
- **Inference server:** software that loads a model and answers generation requests through an API. oMLX fills that role here.
